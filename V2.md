# FrankiFlow Mail v2

The `v2` branch runs a native Next.js App Router / React / TypeScript client. The existing static application sources remain in the repository, including a reader attachment regression fix. `main` and the production site are not changed by creating this branch.

## Run and test

Use the existing `/workspace/frankiflow-mail` checkout; cloud tasks already have isolated workspaces and do not need another worktree.

Requires Node 24 and npm. No database container, private dependency token, or build-time backend credential is required.

```sh
npm ci
npm run dev
```

`/` requires Supabase sign-in. `/demo` is an explicitly separate sample mailbox with fictional addresses. It makes no Supabase requests and never sends email. Demo changes, including attachment bytes, are kept only in the browser's local storage; Reset sample mailbox clears them. Large files can exceed browser storage limits, in which case the UI reports that persistence failed. Do not put confidential files in the demo.

The public Supabase URL/key default to the existing frontend configuration. `.env.local` can override the values shown in `.env.example` for a separate development backend. Public variables are embedded at build time. Never add Supabase service-role, Resend, or Gemini keys to the browser or repository. Existing RLS and authenticated Edge Functions enforce real mail access; the sample mailbox does not bypass them.

```sh
npm test
npm run build
npm run typecheck
npm start
# In a second terminal, with the production server running:
npm run test:e2e
npm run test:contract
```

The browser tests use local `/usr/bin/chromium` by default. Set `CHROMIUM_PATH` to another installed Chromium executable. CI installs the matching Playwright browser and sets this variable. `BASE_URL` runs the same smoke checks against a deployed branch. Those checks use `/demo` and the sign-in screen, not a real mailbox. `test:contract` intercepts all Supabase HTTP calls with synthetic responses to validate the authenticated frontend contract, binary encoding, loading attachments despite stale flags, storage errors, and retryable send failures. It does not validate a real Edge Function or RLS policy. Screenshots are written to ignored `test-results/`.

## What changed

- A quieter two-pane workspace with responsive navigation, readable conversation cards, theme/density preferences, empty/loading/error states, accessible button labels, and keyboard shortcuts (`C`, `/`).
- Inbox, sent, starred, drafts, archive, spam, trash, search operators, bulk archive/trash/read, text compose, CC/BCC, manual draft save on closing, reply, forward, refresh, and realtime refresh for authenticated mail.
- Sent and received attachment metadata loads by message ID regardless of `has_attachments`. Every reader mount loads its files, and storage failures are visible. Download URLs are short-lived and created only on demand.
- Files use chunked binary-to-base64 encoding, validated 8 MB/file and 18 MB combined limits, explicit send progress, and composer retention after failure.
- Mail HTML is in a sandboxed frame without scripts or same-origin access. External images are blocked until the reader requests them.
- Supabase auth callbacks stay synchronous to avoid a lock deadlock. Draft cleanup after delivery cannot turn a successful send into a failed-send message that encourages resending.
- The classic reader now keys readiness to the actual DOM and maps thread messages by ID rather than index. This fixes missing attachments after a rerender and mismatched files when API ordering differs.

## Deployment

The repository is already documented as hosted on Netlify. `netlify.toml` builds with `npm run build` and publishes `.next`; Netlify's automatic Next.js adapter is required. The production branch must remain `main`. Enable branch deploys for **only `v2`** in the existing site's Build & deploy / Continuous deployment settings. Trigger its first branch deploy after pushing `v2`. No production deployment is needed.

If the existing Netlify site slug is `frankiflow-mail`, its expected branch address is `https://v2--frankiflow-mail.netlify.app`, with the sample mailbox at `/demo`. Confirm the actual successful deploy URL in Netlify; a configured branch and a Git push do not prove deployment succeeded.

The `Mail v2 checks` GitHub workflow runs unit, production build, type, and browser checks on pushes to `v2`. Once Netlify has deployed, run that workflow manually on `v2` with `deployment_url` set to the branch URL. It also exercises that URL. The cloud setup uses the same commands.

## Limits requiring live verification or further migration

The Supabase Edge Function source, attachment storage policies, and schema migrations are absent from this checkout. The existing `send-mail` function must persist every outbound attachment in `frankiflow-mail-attachments`, insert the corresponding `frankiflow_mail_attachments` row linked to the **sent message ID**, and set `has_attachments` on that message. Client rendering cannot recover files that the backend never stored. Do not resend delivered email to repair historical attachments. Verify with a dedicated test mailbox and a known attachment after branch deployment; check the file bytes after a fresh sign-in and reload. Never disable RLS or expose mail to test without login.

The new UI reports a message that declares attachments but has no stored file rows. Live sending, RLS, signed download authorization, Netlify's adapter, and production behavior require separate live verification. Mock contract tests do not establish these.

This is an initial Next.js migration, not full feature parity. The original sources retain the calendar/scheduler, rich composer/signatures, labels/filters/templates, AI assistant, background push/PWA, contacts management, advanced account settings, and scheduled sending. These need dedicated migration and live backend validation before replacing production. Forwarding currently quotes text; attachment forwarding requires selecting the files again. Drafts save text and recipients; attached files stay in the open composer and must be sent or removed before saving. The Next.js UI does not register the legacy service worker.
